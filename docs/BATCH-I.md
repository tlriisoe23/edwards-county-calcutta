## What changed

**CAL-P3-003 — clearing "Minimum starting bid" or the house deduction saved 0 and said "Saved".** Both fields were `type="number" min="0"` whose `onChange` did `Math.round(Number('') * 100)`, so a cleared field became 0 in the draft and the server's `cents.min(0)` accepted it. Per D-CAL-2 the rule is now enforced in two places. Client (`app/rules.tsx`): the two amount fields keep their raw text in a small shadow state so a blank is never coerced; while the minimum is blank or below $1.00 the field is `aria-invalid`, shows **"Enter a minimum starting bid of at least $1.00"** inline (`role="alert"`) and carries the same text as its native custom validity, so pressing *Save event & rules* is blocked by the browser with that exact message (the submit handler also refuses with a toast if validation is bypassed). The deduction amount does the same with "Enter a house deduction greater than 0, or choose None." whenever the type is Percent or Fixed; choosing type *None* clears the error and saves, which is the only way to express "no house cut". The inputs' native `min` values move from 0 to 1 / .01 and gain `required`. Server (`app/api/admin/route.ts` `settingsSchema` `superRefine`): `minBid < 100` and `deductionType !== "none" && deduction <= 0` are rejected with the same messages; an omitted or null amount already failed the `cents` schema. No schema change; existing events keep their stored values until the next rules save, which then has to satisfy the rule.

**CAL-P3-004 — import preview disabled Import without saying which rows were wrong.** `app/editors.tsx` now computes the blocking reasons per preview row — `name required`, `flight not found (pasted name)`, `player required`, `at most 4 players`, `index must be a number` — and prints them under the team name (`.import-issue`, linked by `aria-describedby`; the name and index inputs are `aria-invalid` for their own reasons; the row gets a red left rule). The button reads **"Import N teams · M rows need attention"** (singular "1 row needs attention") while any row blocks, and returns to "Import N teams" when the rows are fixed. The import itself is unchanged and atomic (the server still rejects the whole batch on any invalid row — Batch D checks rerun below); the pasted flight name is kept only for the message and is not sent.

**CAL-P3-005 — Access accepted the owner's own email and reported "Saved" for duplicates.** `lib/store.ts` exposes the `ADMIN_EMAILS` allowlist as `ownerEmails()` (the same parsing `identity()` already used). In `app/api/admin/route.ts` `operator_add` — after the existing replay check and before any write — rejects an owner email with **"<email> is already an owner. Owners are managed in the site settings, not here."** and an existing operator (emails are already lower-cased, so the match is case-insensitive) with **"<email> already has access."**; both return 400, so nothing is inserted and **no audit row** is written (the audit insert and the allowlist insert were one batch, so skipping the batch skips both). A concurrent retry that finds the row already committed re-checks the replay marker first and still returns `duplicate: true`, which keeps Batch A's eight-way retry guarantee. `GET /api/admin` now also returns `owners` (allowlist, owner only). The Access tab (`app/operator.tsx`) lists **Owners** first as read-only rows (`.owner-row`, an *Owner* badge, no button, "Owner access comes from the site settings and cannot be granted or revoked here.") and **Operators** beneath with the existing *Revoke* buttons and an empty state; the old "Owner: email" notice is replaced by that list. The operator's kept input plus the red toast make the outcome explicit.

**CAL-P3-007 — Hammer below the fold at 1280×720 / 1024×768: DEFERRED.** D-CAL-5 allowed a sticky bid-entry panel *provided the block still shows team and current bid*, else defer. Measured on the AUDIT-E2 Live fixture ([batch-i.json](batch-i-evidence/batch-i.json), [sticky-experiment.json](batch-i-evidence/sticky-experiment.json), CSS injected in the page and **not shipped**): at 1280×720 the block occupies 350–702 px (team name 447–539, current bid 607–682) and the bid panel is 302 px tall (714–1016). `position: sticky; bottom: 0` alone pins the panel at 418–720 and covers 121 px of the team name and the whole bid; a compacted panel (keyboard hint and "Start bid" heading hidden, tighter margins, 46 px Hammer; 204 px) still covers the bid by 166 px; adding a compacted block (smaller name, players and bid, tighter padding — about twenty declarations across two rules) leaves the team name uncovered but still hides **76 px of the current bid** (65 px at 1024×768). Meeting the proviso would need roughly 260 px removed from the mast / heading / event toolbar / tabs stack above the block, i.e. a redesign of the operator header rather than a small layout change, so the finding stays open as an optional observation. The console CSS is unchanged; the harness confirms the panel is still `static` at 1280×800, 1366×900, 768×1024 and 390×844.

One existing assertion changed: `tests/batch-b.mjs` set `minBid: 1` (one cent) on its disposable settlement fixture, which D-CAL-2 now rejects; it is `minBid: 100` ($1.00) with a comment. Its bids (10001 / 20002 / 30003 cents) are unaffected. No acceptance or refinement assertion encoded the old behaviour (the acceptance suite's `deductionType: 'fixed', deduction: 1` case remains legal and is repeated in the focused suite).
