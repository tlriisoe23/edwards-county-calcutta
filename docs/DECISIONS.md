| D-CAL-5 | CAL-P3-007 | Approved as part of Batch I: make the bid-entry / Hammer panel sticky at the bottom of the console column for viewports under 800 px tall, provided the block still shows team and current bid. If that cannot be done as a small layout change, defer. |
| D-CAL-6 | CAL-P3-006 (Batch J) | An unclaimed purse share (a paid place held by an unsold team) **goes to the house**. Per event, in Rules, the house chooses **Keep** (default) or **Return to pot**. Return to pot redistributes that place's amount across the remaining claimed paid places *in the same pool*, proportionally to their ladder percentages renormalized, cent-exact under the existing largest-remainder method; if no claimed paid place exists in that pool the amount stays with the house. Placing an unsold team is legal. Results and Settlement show "Place N — unsold team — $X to house (kept / returned to pot)". The chosen rule is shown in Rules and on the public board/handout rules line so bidders know it before the auction. Withdrawn teams remain rejected. Rationale: most Calcutta rule sheets state that unsold teams are owned by the house; keeping is the conservative default because redistribution changes other buyers' payouts. |

## The fifty-team two-day fixture (2026-09-18)

| ID | Scope | Decision |
|---|---|---|
| D-CAL-12 | The demo is the evening, not a snapshot of one | The twelve-team demo loads mid-auction, with sales already recorded and a team on the block — right for practising the console, wrong for rehearsing the night. The fifty-team one loads at **SETUP**, with nothing sold, nothing on the block, and buyers already in the list: the state the room is in ten minutes before the first lot. Both stay; the Tools menu offers each by what it is for. |
| D-CAL-13 | The same fifty teams as the leaderboard, copied rather than shared | `lib/demo-two-day.ts` is a literal table of the fifty teams the leaderboard's own `demoTwoDay()` builds — the same names, the same four flights at 13 · 13 · 12 · 12, and each team's pop as that product worked it out. It is copied because the two repositories share no code by design (AGENTS.md), and copying is stated plainly in the file rather than hidden: it can drift, and `tests/two-day-demo.mjs` pins the shape it must not drift out of. The pop rides in the **handicap** column, which is where this product already keeps a per-team number the room can see. |
| D-CAL-14 | A fixture that will not commit is not a fixture | Fifty teams and a hundred players is a hundred and seventy-odd inserts, and the local D1 runner drops the connection outright at that size — the first attempt failed with "Network connection lost", not a validation error. `insertMany()` folds rows into multi-row INSERTs, and folds them **in chunks**, because D1 allows only about a hundred bound parameters per query; one statement per table would have traded one limit for the other. The whole event still commits as a single batch, so a retry cannot leave half a demo behind. |

## A backup script for the settlement records (2026-09-18)

| ID | Scope | Decision |
|---|---|---|
| D-CAL-15 | The product holding the money finally gets the backup script | OC-1: until now this repository had none, while its sibling leaderboard ran one nightly — so every pre-deploy snapshot of a database holding real sales, ownership splits and payments was taken by hand. `scripts/backup-scheduled.sh` is the port of that script, scheduled at 02:45. It verifies more than the leaderboard's does, because what it is protecting is different: as well as `integrity_check` it refuses a backup in which any sale points at a missing team, or any ownership row at a missing sale. A file that opens but has lost its references is not a backup of anything anyone could settle from. Getting the file off this host is the sibling's `scripts/replicate-offhost.sh`, named in the header so it is findable from here. |
| D-CAL-16 | Verify a copy, never the artifact | Opening a snapshot to check it creates `-wal` and `-shm` sidecars beside it, and `readOnly: true` does not prevent that. A stray `-wal` next to a backup is replayed by SQLite on the next open, so the verification would be editing the thing it verifies. The script copies the snapshot to scratch and opens the copy, which also exercises one more read of what was just written. |

## Importing the flighted field (2026-09-18)

| ID | Scope | Decision |
|---|---|---|
| D-CAL-17 | Automatic detection, manual application | The owner asked for this to be automatic with a manual fallback. The automatic part is **noticing**, not **acting**: the roster reads the leaderboard once when it opens and says what differs — *"3 teams not here yet · 2 with a different flight or pop"* — and applying is still a button. The reason is not caution for its own sake. A team's flight and pop are the terms it was **sold under**: the price was agreed in that flight and the pool is settled by it. A background sync would be able to re-price a bought team in the middle of a lot, which is a money bug wearing a convenience's clothes. Detection gets the whole benefit; application is the part that must stay deliberate. The seam is read-only and one-directional, which is the isolation both repositories' AGENTS.md describe, narrowed rather than broken. |
| D-CAL-18 | An import matches on the team name | An import carries no ids, so the old behaviour created a **second copy of every team** on a second import — exactly what happens when a score is corrected after the flights are drawn and the list is brought over again. The team name is what the room calls a team and what the board prints, so it is the identity to match on. Importing now adds what is new, updates what moved, and **refuses to touch a team that is sold or on the block**, naming it in the result: *"47 added · 2 updated. Left alone because they are sold: Smith / Jones."* A row count would have described all three outcomes identically, including the one that matters. |
| D-CAL-19 | The address is a private host, and its absence is a supported state | `LEADERBOARD_URL` points at a host on an internal-only Docker network, so the request never leaves the machine (D-LB-73 covers the network). It is read through the worker env like every other setting rather than `process.env` — in development those are two different places, which is how the first attempt failed. An installation with no leaderboard leaves it unset, and the import says so and falls back to the paste box; that is a supported shape, not an error. |

## The import's missing half (2026-09-19)

| ID | Scope | Decision |
|---|---|---|
| D-CAL-20 | An import that names a problem should be able to fix it | The owner's first real use hit *"No flight here is called Championship or A Flight or B Flight or C Flight or D Flight. Add them under Event & rules, then import again"* — a correct refusal and a useless remedy, since retyping five names exactly, in order, is the transcription this import exists to remove. The dialog now **offers** them: `flight_import` creates the missing ones in the leaderboard's own order, each with its own pool paying three places, exactly what adding one by hand produces. It is strictly additive — a name that already exists is untouched, so it can never rename, recolour or re-pool a flight teams were bought in — and refuses outright if there is nothing missing. |
| D-CAL-21 | Which leaderboard event, said out loud | The pull read whatever event the leaderboard happened to be showing. That is usually right and occasionally very wrong: a club running two events, or a Calcutta for one that is not on the board. The dialog now names the event it is reading and lets you change it, and an event with no flighted field keeps the picker on screen with the reason attached rather than closing the door — the answer is usually another event, one click away. |
| D-CAL-22 | A dialog carries its own change forward | This dialog commits against the revision it was opened at, so a change made elsewhere while it sits open is rejected instead of silently overwriting (Batch G). Creating the flights is a change made **by** the dialog, so without carrying the new revision forward the import that follows was refused as if a stranger had moved — a 409 on the operator's own click. `flight_import` returns its revision and the dialog adopts it. The protection is unchanged for anything foreign. |

## Tournament eve (2026-09-19)

| ID | Scope | Decision |
|---|---|---|
| D-CAL-23 | The desk is rehearsed signed in, on the deployed image, and it names what it carries | OC-2 had been open since S1: every operator-side claim here was local evidence, because production sits behind Google. `tests/console-rehearsal.mjs` is the leaderboard's model ported without invention — a throwaway container on a **copy**, a run-only password, every tab and prepare step at two widths, one write (a buyer) so the copy is proven writable and the revision proven to move, the public board and the TV, and the desk shut again to an anonymous caller. Two things it found on its first run are **carried by name** rather than filtered: the sales table's unfocusable scroll region (OC-5) and the Teams tab's leaderboard probe answering 400 where none is configured (OC-7). A carried finding is printed on every run, so it cannot become the thing that hides the next one, and it stops matching the day it is fixed. Given a file on the command line, the same script is the signed-in half of a restore drill (O-14 in the sibling repository): that is how the desktop's off-host copy was proven to restore, not merely to open. |
| D-CAL-24 | The event is created from the leaderboard, not typed after it | Every field a new Calcutta event needs is already on the leaderboard's board endpoint — the tournament's name, course and dates, its flights in the order it prints them, and every flighted team with its pop — and every one of them retyped is a chance to be wrong, which is where the 2026-09-19 defects lived. *Import event from the leaderboard* sits beside *New event* and is the recommended way to set up: one request over the same private wire the team import uses (D-CAL-17), one preview, one click. It reads the same helper the team import reads, so the two cannot disagree about a row. What the leaderboard does not know is left to the operator: the auction time is asked for in the dialog, and the money rules — minimum bid, increments, house share, payouts — are copied from the most recent real event, because they are the club's rather than the tournament's, and said so on screen. A tournament whose flights are not drawn yet still becomes an event, with the note; a Draft on the leaderboard is invisible here as everywhere, which is the leaderboard's rule. The request is idempotent by its ID like *New event*, and its dates come from ISO text, never a Date, so a time zone cannot move a tournament by a day. |
| D-CAL-25 | A local login is a username, and it is an operator | Two things were wrong with Tools → Local Users, reported the same night. The form kept its button grey until the password reached 14 characters and said so only in fine print, which reads as a button that never works; and on the deployed image a local login signed in and then met a desk that answered 403 to everything, because `identity()` granted operator rights to owners and to the operators table and to nobody else — the account kind D-CAL-4 called "operator-level" had never been granted anything. Now: the account is keyed by a **username** (2–40 letters, digits, dots, dashes, underscores; stored lower-case), with an **optional email** that is a second way in and otherwise a note; `portable_local_users` is rebuilt in place on the first migration, an older email-keyed row becoming a username; the sign-in form asks for a username or email and still accepts the older `email` field; a session made by such an account says so, and `identity()` makes it an operator and never an owner; disabling a login also ends its open sessions. The create button is always live and the form says what is missing as it is typed — the 14-character rule stands (it is the hash's, D-CAL-7), it is just no longer a secret. The console rehearsal now makes a login through the dialog and signs in as it — and first applies `portable/migrate.mjs` to its copy with the image under test, because a deploy does and its first run against the old schema showed why. |

## Small fixes (2026-09-19)

| ID | Scope | Decision |
|---|---|---|
| D-CAL-26 | The scroll region is named where it is made, not where it is used | OC-5 reported one table, but the `.overflow-x-auto` wrapper is not in `app/` at all — it is the shared `components/ui/table.tsx` container behind every table here, so fixing *View and Edit Sales* alone would have left the roster, the audit trail and the import preview unreachable sideways from the keyboard and would have been undone by the next table anyone adds. The container takes `tabIndex={0}` and `role="region"`, and a **label is passed in by the caller**, because a region announced as "region" tells a screen-reader user nothing about which of four tables they just entered. The four callers name themselves. The rehearsal's carried finding for `scrollable-region-focusable` is deleted rather than narrowed: a carve-out that outlives its defect is how the next one hides. |
| D-CAL-27 | The client asks only what the installation can answer | OC-7: the drift probe (D-CAL-17) fired on every open of Teams & flights and, where no leaderboard is configured, earned a 400 the server is right to send — *"No leaderboard is configured…"* — and an error in the operator's console every single time. The fix is on the **client**, not the server: `GET /api/admin` already reports `leaderboard: boolean`, so the effect returns before it fetches. Softening the server's answer to a 200-with-empty-rows was rejected; "you asked for something this installation does not have" is a real refusal and the import dialog, which a person opens deliberately, depends on reading it. Nothing changes where a leaderboard exists. |
| D-CAL-28 | An event can be deleted; a settlement record cannot | WC-4. The guard is not the confirmation, it is the **refusal**: an event holding any sale, settlement payment or payout disbursement cannot be deleted at all, and the message says how many — *"This event holds 1 recorded sale; settlement records are never deleted."* A demo (`demo = 1`) is exempt, because the whole complaint was that a demo loaded once stays forever. The counts are read on the server, never from the caller, and asserted a second time **inside** the deleting batch through the existing `mutation_guards` CHECK, so a sale recorded between the count and the delete rolls the deletion back instead of vanishing with it. The action is eventless like `create_event` and idempotent by request ID, because the event-scoped path reads the event, holds it at a revision and writes an audit row against it, and none of those three survives the row being removed. Children are deleted **explicitly, in reference order**: both runtimes do enforce foreign keys (`portable/sqlite.mjs` sets `PRAGMA foreign_keys=ON`; the local D1 connection reports `foreign_keys = 1` and a parent delete was observed to cascade), but sales, payments and disbursements reference teams and buyers with `ON DELETE NO ACTION`, so relying on the order a cascade happens to unwind in is load-bearing behaviour no schema states. Finally, **the record of a deletion outlives the event**: `audit.eventId` cascades, so the entry is written against the newest *remaining* event — the same anchoring `operator_add` already uses for a change that belongs to no one event — naming the deleted id, its name and what it held. When nothing remains there is nowhere durable to put it and the deletion still proceeds, because an installation must not be left unable to remove its last demo; a repeat of that request ID then settles as a no-op because the event is already gone. |
| D-CAL-29 | A browser-only value is a store with a server snapshot, never an initialiser | OC-9: `/admin` logged React error #418 once on every signed-in load of the deployed image. The cause was the one suspected — the compact-console override read from `localStorage` inside a `useState` initialiser — with a detail the report could not have known: it also fired for the saved value **`off`**, which looks the same as the server's `auto` but still renders the *Auto* button that appears only once the override is manual. The theme picker was cleared: nothing else in `app/` or `lib/` reads `localStorage`. The fix is `useSyncExternalStore` with a server snapshot of `"auto"`, rather than an effect that calls `setState`: it is the pattern React documents for exactly this, it also removes the write-back effect, and — the practical reason it was chosen over the effect — an effect that sets state trips `react-hooks/set-state-in-effect`, which would have added a lint error to a baseline this work is not allowed to move. The saved choice arrives in the render after hydration; persistence and the *Auto* reset behave as before. |
| D-CAL-30 | A team from the leaderboard is known by the leaderboard's own id | The import matched incoming rows to existing teams by name, on the reasoning that the name is what the room calls a team (D-CAL-17). The dress rehearsal of 2026-09-19 showed the cost: a team renamed on the leaderboard after the import came back as a second team, leaving the old one in the queue — and a duplicate is a team that can be sold twice (OC-8). Every row the leaderboard sends now carries that board's own id for the competitor, the team keeps it as `sourceId`, and the import and the Teams tab's drift check match on it before the name. Rows pasted by hand have no such id and match by name exactly as before, so the manual path is unchanged. The column arrives by `drizzle/0002`, an `ALTER TABLE` the release applies with `portable/migrate.mjs`; the console rehearsal applied it to a copy of production first. |
